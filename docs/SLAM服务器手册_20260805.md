### 4.3 points_time_fix（用户自写，关键补丁）

- **脚本**：`src/points_time_fix/scripts/time_fix.py`
- **作用**：KITTI bag 的 /points_raw 只有 x,y,z,intensity,ring（**无 time 字段**），FAST-LIO/LIO-SAM 需要 per-point time。脚本按**方位角模型**补时间戳：
  - `time = azimuth / 360 × scan_period`，scan_period = 0.1s（10Hz）
  - 若点云已有 time/t 字段则直接透传
- **话题**：订阅 `in`（launch 里 remap 为 `in:=points_raw`）→ 发布 `out`（`points_raw_fixed`）
- **输出点结构**：x,y,z,intensity,ring,time，point_step=22
- **数据流**：`rosbag play` → /points_raw → points_time_fix → /points_raw_fixed → 喂给 FAST-LIO 和 LIO-SAM
- **⚠️ 历史坑**：某次 roslaunch 出现 points_time_fix 双实例（-1 和 -6）反复崩溃重启（每 2 秒一次），原因疑似 launch include 重复或旧 roslaunch 残留。重跑前确认只有一个 roslaunch、一个 points_time_fix 实例。

### 4.4 kitti_eval（评估脚本）

位于 `/hy-tmp/tools/kitti_eval/`：
- `kitti_est_gt_to_tum.py`：把 FAST-LIO 的 mat_out.txt（或 LIO-SAM odom）与 KITTI GT 对齐转成 TUM 轨迹
  - **对齐逻辑**：bag 第 i 帧 ↔ GT 第 i 帧；FAST-LIO 丢开头 3 帧（mat_out 首行相对时间 0.3118 ≈ 3×0.1039）
  - **⚠️ 硬编码路径**：脚本里写死 `/home/syw2000/Desktop/catkin_ws/src/FAST_LIO-main/Log/mat_out.txt` 和 `/home/syw2000/Documents/datasets/...`，使用前必须 `sed` 改成 /hy-tmp 路径（已改好副本在 `/hy-tmp/tools/kitti_eval/kitti_est_gt_to_tum.py`，2026-08-06 已同步新数据路径）

## 9. 踩坑与教训（AI 必读，都是真金白银换的）

1. **SSH 必须 PTY**：非 PTY 会话下，`oss login` 的 Username 会吞掉后续输入、`send-keys ctrl+c` 会变成字面文本 "ctrl+c" 打到 shell 里，导致命令错乱（今天 oss 登录差点翻车）。
2. **oss rm 要确认**：`oss rm` 会问 `Please input (y/n)`，必须 `echo y | oss rm ...` 或手动输 y，否则命令挂起看起来像卡死。
3. **oss login 账号自动填充**：服务器之前登录过 OSS，Username 会自动显示账号，只需回车 + 输密码；不要手动再打一遍账号（会拼成 "账号+密码" 的脏输入）。
4. **evo 用 `-a` 不要 `-r full`**：`-r full` 输出 unit-less 误导数值；`-a` 是 SE(3) Umeyama 对齐。RPE 计算慢（约 2 分钟）不是卡死。
5. **LIO-SAM 不 record 就没产物**：默认 savePCD=false 且不输出轨迹文件，必须 `rosbag record /lio_sam/mapping/odometry` 或开 savePCD，否则跑完一场空（用户第一次跑就是这样）。
6. **FAST-LIO 必须 kill -INT**：不主动落盘，SIGINT 才写 Log/mat_out.txt。
7. **points_time_fix 双实例坑**：曾出现两个实例反复崩溃重启（roslaunch 日志里 -1/-6 每 2 秒 restart），重跑前确认单实例。
8. **evo 环境**：需 `pip install "argcomplete<2.0"` + `PYTHONPATH=/opt/ros/noetic/lib/python3/dist-packages`。
9. **恒源云生命周期**：`/hy-tmp` 关机 24h 清、系统盘 10 天；按量计费关机停计费；「释放」= 删实例慎用。
10. **kitti_eval 硬编码路径**：脚本写死 `/home/syw2000/...`，用前 sed 改 /hy-tmp 路径。
11. **百度网盘上传**：`baidu up` 支持断点续传式进度（分块 181 块）；上传期间并发跑 `baidu ls` 可能导致 cli panic（go 堆栈），等传完再 ls。
12. **oss 不支持 .md/.txt 扩展名**：`oss cp` 传文档会报 "Unsupported file type"，需先 tar.gz 打包再传（.tar.gz 等压缩包类型支持）。
13. **SSH 会空闲断线**：长时间无操作会掉，重连即可；后台任务用 setsid nohup 不受影响。
14. **直线轨迹 evo 的 -a 会退化**：`Degenerate covariance rank, Umeyama alignment is not possible`——直线运动绕前进轴旋转不可观，3D Umeyama 求不出；改用 2D 对齐（绕 z 旋转+平移）评估（脚本 `tools/water/eval_2d.py`）。
15. **水上数据双时间轴（大坑）**：W06/N03 的 LiDAR csv 点时间（57~115s）与 IMU/GPS/Laser_Timestamp（0~58s）是两个时钟轴，相差 57.045s（序列名 57_115 即 LiDAR 轴范围）；**bag 帧时间戳必须用 IMU 轴**（base_unix + Laser_Timestamp_Start[i]），点 time 字段用帧内相对时间（col8 - min(col8)），否则 FAST-LIO 去畸变时间错位全部丢点（表现为 mat_out 只有几行 + No point 日志）。
16. **ring 负号必须归一化**：水上数据 ring 是 -15~-1/1~15（负数），直接喂 FAST-LIO/LIO-SAM 会数组越界崩溃，需归一化到 0~15。
17. **镜像 NVIDIA GL 库是 0 字节空壳（大坑）**：/usr/lib/x86_64-linux-gnu/ 下 libGLX_nvidia.so.570.195.03、libEGL_nvidia.so.570.195.03、libnvidia-glcore.so.570.195.03 全是 0 字节；内核模块是 535.154.05（runfile 装的），GL 栈完全缺失 → 任何 OpenGL 程序只能 llvmpipe 软渲染（RViz 卡的根因）。修复：加腾讯云 nvidia-cuda 源装精确版本 deb（见第 12 章）。
18. **NVIDIA 官方下载服务器 403**：us/international.download.nvidia.com 对数据中心 IP 直接 403 Forbidden（带浏览器 UA 也没用）；清华/阿里云 nvidia-cuda 镜像路径 404；**腾讯云镜像可用**：`https://mirrors.cloud.tencent.com/nvidia-cuda/ubuntu2004/x86_64/`（有全部历史版本 deb，含精确 535.154.05）。
19. **vglrun 无头环境必须 VGL_DISPLAY=egl**：vglrun 默认找 :0 的 3D X server（无头会报 "Could not open display :0"）；VirtualGL 3.1+ 用 `VGL_DISPLAY=egl` 走 EGL 直连 GPU，不需要 X server 的 GLX。验证命令：`DISPLAY=:1 VGL_DISPLAY=egl vglrun glxinfo -B | grep renderer` 应显示 NVIDIA。
20. **libnvidia-gl-535 版本必须精确匹配内核模块**：候选最新 535.261.03 不能用（与内核 535.154.05 版本校验不匹配），必须 `apt-get install libnvidia-gl-535=535.154.05-0ubuntu1`；该包依赖只有 libnvidia-common-535（glcore 在包内，无独立 libnvidia-glcore-535 包）。
21. **VNC 端口公网不可达**：恒源云默认只放行 22 端口，5900 直连不通；必须 SSH 隧道 `ssh -p 48882 -L 5900:localhost:5900 root@i-2.gpushare.com` 后 VNC 连 localhost:5900。
22. **LIO-SAM pcd 保存机制（2026-08-06 确认）**：savePCDDirectory 是 `$HOME` 相对路径（写 "/Documents/..." 实际存 /root/Documents/...）；savePCD: true 时 **Ctrl-C 退出自动保存**（visualizeGlobalMapThread 退出时调 saveMapService）；保存前代码 `exec rm -r` 清空整个 pcd 目录再重建（历史 pcd 不按日期归档会被清掉）；**轨迹从不自动保存**，必须 rosbag record。
23. **evo 无头环境 plot 崩溃**：evo 默认 plot_backend=TkAgg，headless 下 `evo_ape --plot --save_plot` 直接崩（`Cannot load backend 'TkAgg' ... headless`）→ 指标能算但 zip/png 全不生成。修复：`evo_config set plot_backend Agg` + `plot_export_format png`（已设）。另注意 evo 输出里 rmse 是**小写**（grep 用 -i）。
24. **evo_traj 在 conda 里**：evo 装在 conda base（/usr/local/miniconda3），非交互 shell 不激活 conda 时 `evo_traj: command not found`。eval 脚本里需 `source /usr/local/miniconda3/etc/profile.d/conda.sh && conda activate base`（放在 source ROS setup 之后、PYTHONPATH 保持 ROS 库）。
25. **evo --save_plot 生成两张图**：`--save_plot xxx.png` 实际生成 `xxx_raw.png`（未对齐）+ `xxx_map.png`（对齐后）两个文件；evo_traj 的 -o 参数不存在（会报错），直接 cd 到工作目录跑 + `--save_as_tum`。
26. **LIO-SAM launch 的 rviz arg 是后加的**：服务器原版 run_kitti.launch/module_rviz.launch **没有 rviz 参数**（rviz 无条件启动），命令行传 rviz:=true 被 roslaunch 忽略（不报错）但 include 传参报 `unused args [rviz]`。2026-08-06 已补：run_kitti.launch + module_rviz.launch 加 `<arg name="rviz">` + unless 条件，simtime launch 透传。
27. **pkill 会误杀自己**：脚本路径/命令行含匹配串时 `pkill -f xxx` 会杀掉脚本自身（如 vv_verify_lio_sam.sh 被 `pkill -f lio_sam` 杀）；脚本命名避开算法名或 pkill 用精确模式。
28. **FAST-LIO 停止后 roslaunch 会残留**：`pkill -INT fastlio_mapping` 只杀子进程，roslaunch 父进程还活着；run_slam.sh 已修（再 pkill -f "roslaunch fast_lio"）。
29. **LIO-SAM 参数是 `lio_sam/` 前缀（大坑）**：utility.h 用 `nh.param("lio_sam/sensor", ...)` 读参数 → **嵌套结构 yaml（lio_sam:/navsat:/ekf_gps: 开头）才是正确格式**；平铺 yaml 会导致 sensor 读不到 → 四节点全报 `Invalid sensor type` 反复崩溃重启（respawn=true）→ 表现为 odometry 不输出、traj bag 空、pcd 是 archive 拷的残留旧地图（假成功）。判据：`rosparam get /lio_sam/sensor` 有值才对。
30. **IMU 消息必须有有效四元数**：csv2bag.py 生成的 Imu 若 orientation 全零，LIO-SAM imuPreintegration 报 `Invalid quaternion, please use a 9-axis IMU!` 并丢弃全部 IMU → 无预积分 → 无 odometry 输出（traj bag 4KB 空）。修复：orientation 设单位四元数 (0,0,0,1)。
31. **LIO-SAM 水上 90°FOV 精度差（预期）**：W06 上 FAST-LIO ATE 2D 0.20m vs LIO-SAM 3.58m——LIO-SAM 特征提取/环闭合假设 360° 扫描，90° 前视雷达是硬伤；这不是流程 bug，是算法-传感器适配问题，对比结果本身有科研价值。
32. **eval_fast_lio.sh 必须用归档 mat_out（大坑）**：脚本原硬编码读 `Log/mat_out.txt`（实时最新），但**任何新运行都会覆盖它**——用户 21:35 跑 N03、22:03 跑 H05 后 Log 里是 H05 数据，导致 W06 评估错用 H05 轨迹算出 56m 假误差。已修复：脚本自动找 `results/fast_lio/*/*/$DS/mat_out.txt` 最新归档版，Log/ 仅作 fallback。**教训：评估永远用归档产物，不用实时文件**。

解压后目录结构（以 W06 为例）：
```
W06_2_Sequence_57_115/
├── Lidar/               # 580 帧点云 csv（16 线，~1.6 万点/帧，10Hz）
├── IMU.csv              # 2901 行 @50Hz：t,ax,ay,az,wx,wy,wz,...,unix
├── GPSBase.csv          # 290 行 @5Hz：t,ENU_x,ENU_y,...,lat,lon,...,alt
```

点云 csv 每行 8 列：`x,y,z,intensity,ring,azimuth,col7,time`；ring 范围 **-15~15（有负号）**，azimuth 仅 0~90°（**90° 前视 FOV**，非 360°）；N03 序列名 440_523 = LiDAR 轴 440~523s（823 帧）。

### 11.2 ⚠️ 双时间轴（最重要）

| 传感器 | 时间轴 | 范围 | unix 起点 |
|---|---|---|---|
| IMU.csv / GPSBase.csv / Laser_Timestamp_Start.txt | **IMU 轴** | 0~58s | 1594013454.567 |
| LiDAR csv 点时间 col8 | **LiDAR 轴** | 57~115s | 1594013511.612 |

两轴相差 **57.045s**（序列名 57_115 就是 LiDAR 轴范围）。**转换规则**：
- 帧 stamp = `base_unix + Laser_Timestamp_Start[i]`（IMU 轴）
- 点 time 字段 = `col8 - min(col8)`（帧内 0~0.1s）
- IMU stamp = `base_unix + t`

**踩坑后果**：若帧 stamp 用了 LiDAR 轴时间（base+57.045），IMU 只能覆盖前 1 秒 → FAST-LIO 只出 4 帧 + No point 日志；若点 time 用了绝对时间（57s），去畸变时间错位全部丢点。

### 11.3 转换器与配置

- 转换器：`/hy-tmp/tools/water/water_csv2bag.py`（W06/N03 通用，参数 SEQ/N_FRAMES/OUT）
